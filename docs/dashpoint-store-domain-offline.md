# dashpoint.store is offline — root cause and state

Investigated at session end. **The `dashpoint.store` domain registration changed
today.** Every host under it resolves to parking IPs and serves nothing. This is
not a Cloudflare, Worker, or code problem: the zone is no longer delegated to
Cloudflare.

## The evidence

**Authoritative nameservers** (DNS-over-HTTPS, `cloudflare-dns.com`):

    dashpoint.store    NS  ns1.lander.d.parity.domains.
                           ns2.lander.d.parity.domains.
    dashpoint.sale     NS  elisa.ns.cloudflare.com.
                           khalid.ns.cloudflare.com.

`dashpoint.store` is delegated to **Parity Domains landing nameservers**. It is
not delegated to Cloudflare. `dashpoint.sale` still is.

**A records**:

    dashpoint.store                 2.59.170.20 , 104.219.250.37
    www.dashpoint.store             (none)
    pos.dashpoint.store             2.59.170.20 , 104.219.250.37
    demo.dashpoint.store            (none)
    store.dashpoint.store           2.59.170.20 , 104.219.250.37
    homemadecrypto.dashpoint.store  2.59.170.20 , 104.219.250.37
    dashpoint.sale                  172.64.80.1   <- Cloudflare

Neither `2.59.170.20` nor `104.219.250.37` is a Cloudflare address.

    104.219.250.37  AS22612 Namecheap, Inc.   Phoenix US
    2.59.170.20     AS49981 WorldStream B.V.  Naaldwijk NL

Both refuse connections on 80 and 443 (curl exit 7/35, HTTP 000). So the
records exist but nothing answers: a parked/lander state, not a working origin.

**Registry record** (RDAP, `https://rdap.radix.host/rdap/domain/dashpoint.store`,
the service IANA's bootstrap file lists for `.store`):

    ldhName      dashpoint.store
    status       ['client transfer prohibited']
    registration 2025-09-30T06:39:00.000Z
    last changed 2026-09-30T06:40:35.852Z
    nameservers  dns101.registrar-servers.com
                 dns102.registrar-servers.com
    registrar    NameCheap, Inc.

The registration date is **today**, and the record was last changed at
`06:40:35Z`. The nameservers are Namecheap's defaults, and they are NOT the ones
currently answering (Parity's are) — the delegation is mid-change or was changed
again after registration.

`rdap.nic.store` redirects (302) and returns a 404 body; the working endpoint is
`rdap.radix.host`, per `https://data.iana.org/rdap/dns.json`.

## What still works

    https://dashpoint-prover.sansbank.workers.dev/health   200
    https://dashpoint-store.sansbank.workers.dev/          200
    https://dashpoint.sale/                                200
    https://dashpoint-sale.pages.dev/                      200

The Workers and Pages projects are alive. Only the custom domain is gone.

`https://dashpoint-api.sansbank.workers.dev/` returns **404** for `/`,
`/v1`, and `/health`. That subdomain has no route for these paths; the API is
reached through its custom-domain route and through the store Worker's service
binding, both of which depend on `dashpoint.store` being delegated to
Cloudflare. Nothing can reach the API right now by hostname.

## Consequence for the shielding test

The shielding process cannot be exercised end-to-end against "the new
infrastructure" in this state, and the reason is upstream of the code:

- The POS and store are reachable only through `dashpoint.store`, which is not
  delegated to Cloudflare.
- No L1 address is generated anywhere in either repo. `destinationAddress` is
  typed by the merchant on `/admin` and validated by
  `apps/pos/src/lib/config.ts` (`isValidDashAddress`, mainnet P2PKH only).
- The customer-facing `depositAddress` is **not** generated by this project
  either. It comes from the 1Click quote response
  (`packages/api/src/endpoints/quote/Create.ts:373-378`), so it cannot be
  produced while the API is unreachable.
- The proving half is the only part that can be tested today, and it is proven:
  the prover Worker responds 200 with `ok: true`.

## What has to happen

The domain must be recovered at the registrar and delegated back to Cloudflare
(`elisa`/`khalid.ns.cloudflare.com`, or whatever Cloudflare assigns after
re-adding the zone). The zone id recorded in `docs/consolidation-handoff.md` §7
is `9901802469a0c63bf42b9252032fcd1f`; after re-delegation the Worker routes and
Pages custom domains for `dashpoint.store`, `www`, `pos`, `demo`, and the
wildcard need to be verified, not assumed.

Until that is done, every `*.dashpoint.store` check will fail for a reason that
has nothing to do with the application code.
